# Research: Fix-Soon Review Batch

## R1: Where a window reset is detected (FR-001 to FR-003)

- **Decision**: Change `ThresholdTracker.evaluate`. Today a different window end (beyond the Codex tolerance) or a different window start replaces the state with a fresh one whose `lastPercent` is `nil`, so the next observation only records a baseline. After the change, the member-set check runs first: when the member set differs (spec 004 FR-015, spec 009 FR-006/FR-012), the state is replaced with `lastPercent == nil` as today, even if the window also changed (FR-002, re-baseline wins). Otherwise a window change is classified: for budget owners (which pass a `windowStart`) any change of start or end is a reset; for subscription and Codex windows only a known end (not `.distantFuture`, which `observe` uses for a Codex window without reset time) that is later than the recorded known end beyond the tolerance is a reset. A reset keeps the key, stores the new window and sets `lastPercent` to 0 before comparing, so every threshold at or below the first value of the new window is crossed. For subscription and Codex windows, an observation with a known end earlier than the recorded known end (beyond the tolerance) is older data: it is ignored (no comparison, state kept with its later end and `lastPercent`). A change to or from `.distantFuture` replaces the state with `lastPercent == nil`, as today.
- **Follow-up from verification**: two cases the first version missed. (1) A changed credential directory or Codex home may point at another login whose window ends earlier, which the older-end rule would ignore for up to a window; the state now records the directory (`source`) and a change re-baselines, winning over a reset (a sixth re-baseline event). (2) Claude reset times are rounded to the minute and had a tolerance of 0, so a one-minute flip counted as a reset; Claude windows now use the same 120 s tolerance as Codex.
- **Why only forward moves for subscription and Codex**: Codex live and session-snapshot values for the same window can carry different reset times, and a window can lose or gain its reset time when the source changes. With "any change is a reset", alternating ends A, B, A, B would notify on every switch, and re-baselining on the earlier end would still re-arm the next forward move. Ignoring the older end keeps the later window's state, so alternating ends notify at most once.
- **Rationale**: All five re-baseline events already reach `evaluate` without existing state (launch, period switch and live-limits toggle use a new key; saved Claude values at launch are skipped as preliminary) or through the member-set branch, so the change touches only the reset branch. State survives refreshes without usable values, because those `continue` before `evaluate` and keys are pruned only when the configuration drops them (FR-003 holds without changes).
- **Alternatives considered**: A separate "reset seen" flag in `State` (more state for the same result); notifying only the highest threshold (rejected in the brainstorm).

## R2: Period-mismatched carried-over entries (FR-004, FR-005)

- **Decision**: After the carry-over in `RefreshCoordinator` (record source failed), drop every group and own-budget entry whose `period` differs from the owner's configured period. A pure method in `UsageCore`, `UsageSnapshot.droppingBudgetPeriodMismatches(configuration:) -> UsageSnapshot`, does the filtering, so it is unit tested without the coordinator.
- **Rationale**: A budget owner without an entry already has a no-data presentation: the bar shows `…` (`BarLayout` placeholder) and the dropdown shows the owner's name without amount, percent or period line. That presentation names no period, so it cannot show the wrong one (FR-004 as amended in the plan review), and it carries no level (FR-005). The carry-over happens only when the record source throws (for example no Claude Code log directory could be scanned); OpenCode problems are reported as record batch issues and do not trigger it. The tracker already skips entries whose period differs (spec 003 FR-017), and with no entry it skips the owner too. Member entries (`memberItem`) follow the group's entry, so they show the placeholder too.
- **Alternatives considered**: Relabelling the old entry (shows a weekly number under monthly wording, which is the bug); a new "period changed, waiting for data" note (new UI text, the brainstorm chose reuse).

## R3: Credential directories in the Claude scan set (FR-006, FR-007)

- **Decision**: `SessionLogSource.directories(for:)` adds every Claude subscription account's `credentialDirectory` after the default and the extra directories, and deduplicates using `Attributor.canonical` (expand, resolve symlinks, standardize, strip trailing slashes) as the key while still returning the first expanded spelling, so existing callers and tests that compare expanded paths keep working. A missing credential directory is treated exactly like a missing extra directory: the scanner notes it in the diagnostic log and the dropdown shows no error unless no directory at all could be scanned (unchanged rule).
- **Rationale**: Mirrors `CodexSessionSource.homes(for:)`, which already unions the Codex subscription homes (spec 007 research R10). `LogDirectoryScanner` already deduplicates files by canonical path, so no session is counted twice even before the directory-level dedup; the directory-level dedup keeps the log free of duplicate lines.
- **Alternatives considered**: Merging the settings in the configuration file (a migration for no benefit).

## R4: Hardened OpenCode read (FR-008, FR-009)

- **Decision**: After `sqlite3_open_v2` (read-only, as today) and before any query, run `PRAGMA trusted_schema=OFF` and check in `sqlite_schema` that `message` and `session` are ordinary tables (type `table`); if either is a view or missing, fail with a `SQLiteError`, which the existing source error path handles (stale values, log line). A test seam (`connectionHook: ((OpaquePointer) throws -> Void)? = nil`, called right after opening and before the pragma, `nil` in production) lets a test register a side-effecting SQL function on the reader's connection. The control case that proves the pragma matters (the same database read with `trusted_schema` on runs the function) is built in the test on its own plain connection, not through `readRows`. The crafted database makes `message.data` a `VIRTUAL` generated column calling the function, so the query has to compute it; with `trusted_schema=OFF` SQLite refuses with "unsafe use of ...", and the read fails through the existing path. A `session` or `message` view is rejected by the table check.
- **Rationale**: `SQLITE_DBCONFIG_DEFENSIVE` and the other `sqlite3_db_config` options are C variadic functions, which Swift does not import; calling them would need a C shim target, and casting the variadic symbol to a fixed-argument Swift type is not ABI safe on arm64. `DEFENSIVE` mainly blocks writes that corrupt the file (`writable_schema`, direct shadow-table writes), which the read-only connection already excludes. `trusted_schema=OFF` (SQLite 3.31, part of macOS 14's SQLite) is the setting that stops views, triggers, generated columns, defaults and CHECK constraints from calling functions not marked innocuous. The table-type check stops a crafted `message` view outright. Triggers do not fire on reads.
- **Alternatives considered**: A C shim target for `sqlite3_db_config` (new build target for a write-side protection); `SQLITE_DBCONFIG_ENABLE_VIEW` (variadic, same problem; the table check gives the same result).

## R5: Total time limit for the Claude request (FR-010)

- **Decision**: Set `timeoutIntervalForResource = 45` in `UsageEndpointClient.defaultSession`, as in `CodexUsageClient.defaultSession`. A test asserts the configuration value, as `LiteLLMImporterTests` does for the price import; the existing 30 s timeout is set on the `URLRequest`, so it is asserted on the request captured by the stub protocol.
- **Rationale**: `URLSession`'s resource timeout covers the whole transfer from sending the request; the keychain read happens before and is not included. An end-to-end slow-server test would need a local listener and 45 s of wall time; the configuration assertion plus Foundation's documented behavior is enough, and the walkthrough can try it manually.
- **Alternatives considered**: A task-level timeout in the coordinator (duplicates what the session offers).

## R6: Signing tier guard (FR-012 to FR-015, FR-017)

- **Decision**: A new `unusable_developer_ids` function in `scripts/release/lib.sh` parses `security find-identity -p codesigning` like `codesigning_identities`, but prints only `Developer ID Application:` identities whose status is `CSSMERR_TP_CERT_EXPIRED` or `CSSMERR_TP_CERT_REVOKED`, as `hash<TAB>name<TAB>problem`. `preflight` checks, when `SIGN_IDENTITY` is empty and the selected tier is not `developer-id` and the list is not empty: without `ALLOW_TIER_DOWNGRADE=1` it reports (release: stop; dry run: warning that also says a real release would stop unless `ALLOW_TIER_DOWNGRADE=1` is set); with it, it warns that the release is a deliberate tier downgrade. `build-app.sh` warns for development builds when `SIGN_IDENTITY` is empty and it falls back with such a certificate present (`release.sh` always calls it with a forced identity, so releases never print it twice). The stop message names the next tier ("to release as self-signed" or "on the next tier"), since without a self-signed certificate the fallback is ad-hoc, which also needs `ALLOW_ADHOC`. The ad-hoc check (`ALLOW_ADHOC`) stays independent and runs as today. The Makefile adds `ALLOW_TIER_DOWNGRADE` to its exported variables and `test_makefile.sh` lists it.
- **Rationale**: `codesigning_identities` already drops lines with any status except `CSSMERR_TP_NOT_TRUSTED`, which keeps the selection logic unchanged (not-trusted Developer ID stays usable, clarification Q1). Putting the guard in preflight stops the release before building, and dry runs share the code with `warn` as reporter.
- **Alternatives considered**: An expected team ID (maintainer specific); `REQUIRE_TIER` (opt-in, easy to forget).

## R7: Replacing a published release (FR-016)

- **Decision**: In `release.sh`, compute `is_latest` by version: the published tags (`gh release list --exclude-drafts --json tagName`, as `update-cask.sh` does) plus `$tag`, through `highest_release_tag`; `is_latest` is true when the result is `$tag`. When `REPLACE=1` finds a published release, `gh release edit --draft=true` first, set `phase="draft"`, upload with `--clobber`. Every publish (new release, replacement, retry of a draft) uses `gh release edit --draft=false` plus `--latest` when `is_latest`, otherwise `--latest=false`; the cask update follows as today. The existing exit trap message for `draft` already says how to retry or delete.
- **Rationale**: Reuses spec 005's draft guarantee and its retry message. A version-based decision gives the same answer before the draft switch and on a later retry (an `isLatest` read would be lost with the failed run, and GitHub marks a newly published release as latest by default, so a retried old tag would become "Latest"). `update-cask.sh` keeps its own highest-version check (spec 005 FR-021). If the repository ever enables GitHub's immutable releases, the draft switch fails before any asset changes, which is safe.
- **Alternatives considered**: Uploading under temporary names and renaming (three assets that must match each other; a partial swap leaves a mismatched set).
