# Research: Additional Session Directories per Account

All findings come from this repository at commit `84279da` (spec 034 merged) and from the site checkout at `1d2cc03` (2026-10-21). The Technical Context has no open questions; each section records a design choice and the code it rests on.

## R1: Where the list lives

- **Decision**: A stored `additionalSessionDirectories: [String] = []` on each of the three settings structs (`SubscriptionSettings`, `CodexSubscriptionSettings`, `TokenBasedSettings`), plus `AccountKind.additionalSessionDirectories { get set }` and `AccountKind.sessionHarness` (`.claudeCode` for a Claude subscription, `.codex` for a Codex subscription, `provider.sessionHarness` for a token-based account). `TokenBasedSettings.provider`'s existing `didSet` clears the list together with `enteredSessionDirectory`.
- **Rationale**: The editors already receive the settings struct as a binding (`SubscriptionEditor(settings:)`, `CodexSubscriptionEditor(settings:)`, `TokenBasedEditor(settings:)` in `AccountSettingsView.swift`), so each binds `$settings.additionalSessionDirectories` with no new plumbing. The provider switch rule (spec edge case, spec 034 FR-007) stays the one `didSet` in UsageCore that research R4 of spec 034 put there; a list on `Account` could not be cleared from that `didSet`. Because the field is part of each settings struct, `Configuration.dataRelevant()` sees it without a new line, so a change refreshes (FR-003), and `subscriptionFingerprint()` (Claude subscription id plus `credentialDirectory`) does not, so no plan-limit request follows.
- **Synthesized coding**: `SubscriptionSettings` and `CodexSubscriptionSettings` have explicit `CodingKeys` that omit the new property; it has a default value, so their synthesized `Codable` still compiles and keeps its shape. The file format is owned by `Account.init(from:)` and `Account.encode(to:)`, as for every other account key.
- **Alternatives**: one list on `Account` (rejected: the provider switch would need a `didSet` on `Account.kind` comparing providers, or app code); a top-level map from account id to entries (rejected: survives account removal and id edits, and splits the account across the file).

## R2: Entry rules without touching the file system

- **Decision**: A new pure type `SessionDirectoryEntry` in `Config/SessionDirectoryEntry.swift` with `static func refusal(of entry: String, in list: SessionDirectoryList, paths: Paths) -> SessionDirectoryRefusal?` and `static func adding(_ entry: String, to list: [String]) -> [String]`. Checks, in this order, on the trimmed entry: relative (neither `~`, `~/...` nor `/...`; for `.openCode` only when it contains `*`), `**`, the home folder or `/` (after `paths.expand` and standardizing `.` and `..`, no symlink resolution), a bare `*` component directly under the home folder or `/`. `SessionDirectoryRefusal` is an enum with a `reason` text (contracts/configuration.md).
- **Rationale**: Settings must never read the file system (spec Assumptions), so validation is string work only; `Paths` is injected so tests use a temp home. `validate()` and decoding both call the one function, so the "Not applied" line and the load note give the same reason. `~` alone is the home folder and is refused like `~/`. `~name/x` starts with neither `~/` nor `/` and is relative.
- **Alternatives**: canonical comparison with the real home (rejected: touches the file system in Settings); rejecting `*` anywhere in the first component (rejected: `~/.claude-*` is a wanted example, spec User Story 2 scenario 6).

## R3: Wildcard matching with an injectable file system

- **Decision**: `Logs/WildcardExpander.swift` holds `protocol DirectoryFileSystem: Sendable` (`contents(ofDirectory:) -> DirectoryContents` with cases `names([String])`, `missing`, `unreadable(String)`; `isDirectory(_:) -> Bool` following symlinks; `canonicalPath(_:) -> String`), `struct LocalDirectoryFileSystem` (FileManager, `Attributor.canonical`), `enum WildcardPattern` (`matches(name:component:) -> Bool`) and `struct WildcardExpander` (`expand(_ entry: String) -> WildcardExpansion`). Tests use an in-memory fake defined in the test target, plus temp-directory runs with `LocalDirectoryFileSystem`.
- **Matching** (FR-004): the expanded entry is split into components. The leading run of components without `*` is the base. Each later component with `*` lists every current candidate and keeps the names that match and are folders (`isDirectory`, so a symlink to a folder matches and a file never does); a component without `*` is appended as is. At the end only paths that are folders stay. `*` is any run of characters (also none) inside one name; the matcher is a greedy split on `*` with anchored first and last pieces. A component that starts with `*` never matches a name starting with `.`. `?`, `[`, `]`, `{`, `}` are literal.
- **Order and cap** (FR-005): matches are sorted by full path with `String <` (byte order, locale independent, stable across runs), a match whose canonical path is the home folder or `/` is dropped (FR-006), and the first 100 are kept. `WildcardExpansion` reports `matched` (all, before the cap), `paths` (at most 100) and `listingErrors` (a parent that exists but cannot be listed). A parent that does not exist gives no match and no error (User Story 2 scenario 7).
- **Rationale**: The expander is the only new code that lists folders; keeping it behind a protocol lets the matching rules (dot names, one level, symlinks, cap) be tested without building trees on disk, and the three sources share it.
- **Alternatives**: `glob(3)` (rejected: also expands `?` and `[...]`, has its own dot rules, and is not injectable); `FileManager.enumerator` over the base (rejected: walks deep trees for a one-level pattern).

## R4: One resolution of the directories per refresh

- **Decision**: `Logs/SessionDirectoryResolver.swift` with `resolve(_ harness: Harness, configuration: Configuration) -> SessionDirectoryResolution`. It lists main directories first (`Configuration.accountClaudeCodeDirectories` or `accountCodexHomes`, accounts order, unchanged from spec 034), then every account's additional entries in accounts order and entry order, each wildcard's capped matches in path order. Each directory appears once, compared by `fileSystem.canonicalPath`, keeping the first spelling and origin. The home folder and `/` are skipped for every Claude Code directory (as `SessionLogSource.directories(for:)` does today) and for every additional Codex directory; a Codex main home keeps today's behavior. The resolution also returns, per subscription account id, the canonical set of its additional directories (literal and matched) for the tie-breaker (R5), and one `WildcardReport` per distinct entry text (R9).
- **Rationale**: FR-008 asks for one read per canonical directory across all routes; FR-012 asks for main directories before additional ones so a file reached both ways is found in the main directory. Both scanners already take "the first directory that reaches a file wins" (`LogDirectoryScanner.scan`, `CodexSessionSource.collect` `present` set), so an ordered, deduplicated list gives both rules for free. The cap counts matches before dedupe (FR-005: "whether or not it is also reached another way").
- **Alternatives**: expanding inside each scanner (rejected: three copies of the order and dedupe rules); caching matches between refreshes (rejected: FR-005 wants them anew on every refresh).

## R5: Tie-breaker and the attribution fingerprint

- **Decision**: `Attributor.init(configuration:paths:additionalDirectories:)` gains `additionalDirectories: [String: Set<String>] = [:]` (account id to canonical directories). Each subscription `Candidate` gets `additional: Set<String>`. When several subscription accounts of one kind match (`accountId(for:rawLine:fileConfigDirectory:)`, today `byDirectory`): exactly one whose main `directory` equals the file's directory wins; else, when none has it as main, exactly one whose `additional` contains it wins; else nil (FR-012). The `fingerprint` adds each subscription account's configured entries (trimmed text, not the matches).
- **Rationale**: Token-based accounts never reach the tie-breaker, so only subscription candidates carry the set. `LogIndex.update` drops every entry and rereads all files when the fingerprint changes (`LogIndex.swift` line 78). Putting the matches into the fingerprint would reread every Claude Code session whenever a sandbox folder appears; the entry text changes only with the configuration. Files in a newly matched folder are new to the index and are attributed with the current claims. The one case left: a folder that was already read through another route and starts matching a subscription's wildcard keeps its earlier attribution until the configuration changes or the index resets; this needs two same-kind subscriptions with overlapping routes and a folder appearing in between.
- **Alternatives**: matches in the fingerprint (rejected: SC-005 and cost, above); expanding wildcards inside `Attributor` (rejected: puts file system access into attribution and into `OpenCodeSource`, which builds an `Attributor` too).

## R6: Claude Code scanner, main and additional targets

- **Decision**: `LogDirectoryScanner.scan(targets: [ScanTarget])` where `ScanTarget` has `path` and `isMain`; the existing `scan(directories: [String])` maps every path to a main target, so its tests keep working. `ScanResult` gains `additionalNotes: [String]` (log lines for additional targets: `<path>: skipped, not found`, `<path>: error: not readable`, `<path>: error: cannot read <file>: <error>`); `scannedDirectories` keeps counting every target that existed and was readable, main or additional. Missing or unreadable additional targets and enumeration errors under them go to `additionalNotes`, never to `errors`.
- **Failure rule** (FR-008): `SessionLogSource.collect` throws only when `scannedDirectories == 0` and `errors` (main errors only) is not empty, which is "neither a main nor an additional directory could be scanned and at least one main directory reported the error".
- **Rationale**: Today a missing directory is an error (`log directory not found`) that fails the source when nothing else was scanned. Keeping that for main directories leaves spec 034 behavior unchanged; additional directories only add.

## R7: Codex source

- **Decision**: `CodexSessionSource.Location` gains `origin: SessionDirectory.Origin` (`main`, `literal(entry:)`, `wildcard(entry:)`); `homes(for:)` keeps its signature `-> [Location]`, which existing tests call, and builds the locations from the resolution's directories (main ones keep `isDefault`; additional ones have it false). In `collect`: a main home keeps today's lines and issues; an additional home that is missing logs `skipped, not found` (literal) or nothing (a match that vanished during the refresh logs `skipped, not found` too); unreadable and scan errors log a line and add no issue. Per-home lines stay for main and literal homes; matched homes add their counts to one `wildcard "<entry>": ...` line per entry. The final line names the number of homes read.
- **Rationale**: FR-008 (log only, never an issue), FR-016 (line shapes). `FileEntry.home` stays the canonical home, which `Attributor` compares with main and additional sets.

## R8: OpenCode wildcard entries

- **Decision**: `OpenCodeSource.directories(for:)` keeps the default first and literal entries as today (expanded, deduplicated by expanded path, relative literals unchanged); an entry with `*` is expanded through `WildcardExpander` and each match becomes a `Location` with `isWildcardMatch: true`. In `collect`, a matched folder without `opencode.db` is skipped silently; a matched database that fails to read follows the literal path (issue plus stale, FR-005 of spec 006). The canonical database check (`present`) already reads each database once.
- **Rationale**: FR-013. The type check of `openCodeDirectories` stays `decodeIfPresent([String].self)`; refused entries are dropped after it with a note (R12).

## R9: Log lines and the cap note

- **Decision**: `Logs/WildcardCapLog.swift`: `struct WildcardCapLog` with `mutating func lines(for reports: [WildcardReport], configuration: Configuration) -> [String]`. It returns the cap line for an entry with more than 100 matches when the entry was not logged since the last configuration change or its match count changed; it resets when `configuration` differs from the one it saw last. Each source actor keeps one. Exact line texts are in contracts/directory-resolution.md.
- **Rationale**: FR-005 wants the cap line once after launch or a configuration change and again only when the number changes; a value type with the configuration as input makes that testable without a log.

## R10: Refresh triggers

- **Decision**: No change in `RefreshCoordinator` or `App.saveConfiguration`. A list change makes `needsRefresh(comparedTo:)` true (R1) and `needsNetworkRefresh(comparedTo:)` false, so the app requests a `.local` refresh, and `EndpointPolicy` answers `.local` with `.reuse(reason: "local change")` (`EndpointPolicy.swift` line 95). Wildcard matches are re-evaluated by every refresh, scheduled ones included, because each `collect` resolves anew.
- **Rationale**: FR-003 and FR-005 with existing machinery; tests assert the two booleans.

## R11: Settings section

- **Decision**: Reuse `DirectoryListSection` (in `SettingsView.swift`) for the account list, with title `AccountDirectoryText.additionalDirectoriesSection`, caption and prompt per harness. Its Add button calls `SessionDirectoryEntry.adding(_:to:)` (trims whitespace and newlines, ignores blank and duplicates). Placement: after `Section("Subscription")` in `SubscriptionEditor`, after `Section("Codex subscription")` in `CodexSubscriptionEditor`, after `Section(usageSourceSection)` in `TokenBasedEditor`, each before the next section. `NewAccountSheet` is untouched. The OpenCode caption moves from the inline string in `SourcesSettingsPage` to `AccountDirectoryText.openCodeCaption`.
- **Rationale**: Same look as the OpenCode list, so the two wildcard lists read alike; the duplicate rule moves into UsageCore with a test (FR-002). A refused entry still lands in the draft; `validate()` throws and the "Not applied" line names it (FR-006), and Remove or undo clears it.

## R12: Loading, saving and validation

- **Decision**: `Account.init(from:)` reads `additionalSessionDirectories` leniently: absent is `[]`; a value that is not `[String]` (including `null`) is `[]` with one note; otherwise entries are trimmed, blanks dropped, refused entries dropped with one note each (R2, `Paths()` as `noteDirectories` uses). `Configuration.init(from:)` filters `openCodeDirectories` the same way after its unchanged type check. `Account.encode(to:)` writes the trimmed, non-blank entries under `additionalSessionDirectories` only when there is one. `Configuration.validate()` throws `ConfigurationError(kind: .sessionDirectoryEntry, ...)` for the first refused entry of any account list or of the OpenCode list.
- **Rationale**: FR-001, FR-006, FR-007. Dropping at load means `ConfigStore.load` validates a clean configuration, so a hand-edited bad entry never turns the file invalid; validating in `validate()` means the Settings draft is refused through the existing `saveConfiguration` path.
